# 행사용 실시간 폰 퀴즈 앱 (한잔 퀴즈에서 배운 것)

20~100명이 각자 폰으로 들어오고, 진행자도 폰 하나로 진행하는 앱을 빠르고 안전하게 만드는 방법. 실제로 회식용 "한잔 퀴즈"(beomjun37/Quiz)를 만들며 부딪힌 문제와 해법을 정리했다. 처음부터 다시 짜기보다 그 저장소 구조를 출발점으로 삼는 편이 빠르다.

## 먼저 물어볼 것 (한 번에)
- 인원, 연령대, 화면 공유(TV) 유무 → TV가 없으면 모든 연출이 폰 안에서 끝나야 한다
- 개인전/팀전, 닉네임 여부, 상품 방식(순위상 + 행운 추첨 섞기 추천)
- 진행자 PIN, 배포 위치(GitHub Pages 기본)

## 구조 (검증된 기본값)
- 프런트: React + Vite, 해시 라우터(`#/` 참가자, `#/admin` 진행자, `#/sim` 혼자 연습). Pages에 정적 배포.
- 백엔드: Supabase Postgres. **테이블은 RLS로 막고 모든 읽기/쓰기를 SECURITY DEFINER RPC로만.** 접두어(hq_ 등)로 기존 프로젝트와 섞여도 안전하게.
- 동기화: 공개 상태 1행 테이블에 Realtime 구독 + 뷰 RPC 폴링(2~3초) 이중화. Realtime만 믿으면 폰 잠금/재접속 때 화면이 멈춘다.
- 진행자 동작은 `admin(pin, action, arg)` 하나로. 자세한 설계는 references/architecture.md.

## 반드시 지킬 함정 (실제로 터졌던 것)
1. **Supabase API 경로의 pg-safeupdate**: WHERE 없는 UPDATE/DELETE는 에러. 전부 `where true`라도 붙인다. 서브쿼리 안 WHERE는 안 쳐준다 → 괄호 밖 WHERE만 세는 검사로 확인.
2. **중복 클릭/재전송 멱등성**: next/back/skip엔 `from_phase/from_qi`, 추첨엔 `from_drawn`을 같이 보내 서버가 현재 상태와 다르면 무시.
3. **id 노출 금지**: 참가자 uuid가 공개 테이블에 실리면 남의 답을 대신 낼 수 있다. 당첨자 id 등은 비공개 테이블로.
4. 동점자 추첨은 rank가 아니라 row_number로. PIN은 10회 실패 시 잠금, 실패는 raise 대신 `{ok:false}` 반환.
5. 배포 후 "옛 화면이 보여요" = 캐시. 빌드 때 version.json을 쓰고 업데이트 배너로 새로고침 유도.
6. 노래 문제: 유튜브 임베드는 광고·인트로가 끼므로 시작 초 저장 + 미리 재생 준비, 또는 진행자가 자기 폰에서 20초 클립을 올리는 방식.

## 안전·저작권 선 (사용자가 원해도 지킨다)
- 유튜브 음원 추출, 사이트 우회 스크래핑, 네트워크 제한 우회는 하지 않는다. 대안(임베드, 직접 녹음 클립)을 제시.
- 사진은 위키미디어 등 CC 라이선스만, 출처는 마무리 화면 접힌 영역에. 연예인 얼굴은 라이선스 확인된 것만.
- 관리자 PIN 기본값(1234)은 배포 직후 바꾸라고 꼭 안내.

## 문제 은행 / UX / 테스트 / 배포

## 작업 순서
1. 스키마 → RPC → 시드 SQL을 파일로(01_schema, 02_rpc, 03_seed, 04_bank) 쓰고 합본 ALL_IN_ONE.sql도 만든다(사용자가 SQL 에디터에 한 번에 붙일 수 있게).
2. 로컬 PG에 적용해 RPC를 봇 참가자로 한 판 끝까지 돌린다.
3. Playwright 폰 크기(390×844) 스크린샷으로 참가자·진행자 화면 확인 후 PR → 머지 → Pages 배포.
4. 실기기 확인이 필요한 것(유튜브 재생, 화면 꺼짐 방지)은 사용자에게 폰으로 테스트해 달라고 명확히 말한다.
